# API Contract Design Best Practices — Sources

Provenance for [`../SKILL.md`](../SKILL.md). This file is deliberately kept
out of the skill body so it costs no tokens at load time; read it to verify a
rule, not to follow one. Repository-wide provenance tiers and known gaps:
[SOURCES.md](../../../SOURCES.md).

Throughout this file, "this document" and section references like §4 point to
`../SKILL.md`, whose rules these sources support. This text was moved out of that
file verbatim, so "the rules above" likewise means the rules there.


Primary sources retrieved and read while writing this document:

- [RFC 9110 §9 — HTTP Semantics: Methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9) — definitions of safe, idempotent, and cacheable; the method-properties table (trimmed from SKILL.md 2026-09-28); the `PUT`-as-full-replacement vs `POST`-as-server-defined-processing distinction.
- [RFC 9110 §15 — Status Codes](https://www.rfc-editor.org/rfc/rfc9110.html#section-15) — the status-code rules in §3 (the full status table was trimmed from SKILL.md 2026-09-28). Verbatim quotations: "The server generating a 401 response MUST send a WWW-Authenticate header field ... containing at least one challenge applicable to the target resource" (§15.5.2); "The origin server MUST generate an Allow header field in a 405 response containing a list of the target resource's currently supported methods" (§15.5.6). Also `409` vs `412`, `422`, and the rule that unrecognized codes are interpreted by class (trimmed from SKILL.md 2026-09-28). Note what §15.3.2 (`201 Created`) does **not** say: it carries no `SHOULD` for `Location`, only that the created resource "is identified by either a Location header field in the response or, if no Location header field is received, by the target URI". Re-read 2026-09-28 (verified retroactively) for the `400`/`422` split that a cross-skill review added to §3. §15.5.1 defines `400` as "something that is perceived to be a client error (e.g., malformed request syntax, invalid request message framing, or deceptive request routing)". §15.5.21 limits `422` to request content: the server "understands the content type of the request content ... and the syntax of the request content is correct, but it was unable to process the contained instructions". Content is the body, "a stream of octets sent after the header section" (§6.4), so `422` does not reach a query parameter. Sending every invalid query parameter to `400` and all body field validation to `422` is the house reading of that split; the RFC says neither in so many words.
- [RFC 9110 §9.3.3 — POST](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.3) — the actual normative source for `Location` on creation: "the origin server SHOULD send a 201 (Created) response containing a Location header field that provides an identifier for the primary resource created" — which is why §3 marks `Location` as a house-tightened MUST.
- [RFC 9110 §13 — Conditional Requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-13) — `ETag` and `Last-Modified` validators, strong vs weak, the four precondition headers and their evaluation order, `412` vs `304`, and the lost-update pattern behind §11.
- [RFC 5789 — PATCH Method for HTTP](https://www.rfc-editor.org/rfc/rfc5789.html) — Standards Track, March 2010. "PATCH is neither safe nor idempotent"; clients "using this kind of patch application SHOULD use a conditional request such that the request will fail if the resource has been updated since the client last accessed the resource", for example a strong ETag in `If-Match` (the RFC scopes this to patch formats needing a known base-point, and exempts append-style patches; §11 tightens it to all `PATCH`); and there is "no single default patch document format that implementations are required to support" — the basis of the `PATCH` rules in §2 and §11.
- [RFC 6585 — Additional HTTP Status Codes](https://www.rfc-editor.org/rfc/rfc6585.html) — Standards Track, April 2012, not obsoleted. §3 `428 Precondition Required` ("the origin server requires the request to be conditional"), §4 `429 Too Many Requests` (whose response "MAY include a Retry-After header"). Neither code appears in RFC 9110.
- [RFC 9457 — Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) — the error format: `application/problem+json`, the five standard members and their exact semantics, extension-member naming, the requirement that consumers ignore unrecognized extensions, the `about:blank` default, the IANA problem-type registry, and the security requirement not to expose stack dumps. **Obsoletes RFC 7807.**
- [RFC 7396 — JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396.html) — `application/merge-patch+json`, `null` as delete, whole-array replacement, and its unsuitability for documents with meaningful explicit nulls.
- [RFC 6902 — JSON Patch](https://www.rfc-editor.org/rfc/rfc6902.html) — `application/json-patch+json`, the six operations, and the requirement that a failing operation means the whole patch is not applied.
- [RFC 9745 — The Deprecation HTTP Response Header Field](https://www.rfc-editor.org/rfc/rfc9745.html) — Standards Track, March 2025. `Deprecation` as a Structured Field Item carrying a date (`@1688169599`), which may be past or future and changes no behavior; the requirement that a `Sunset` value not precede it; the `deprecation` link relation. Re-read 2026-09-28 (verified retroactively) for the "`@` plus Unix seconds" wording that the 2026-09-28 trim added to §10: §2.1 says the value "MUST be a Date as per Section 3.3.7 of [RFC9651]", and that example is "Friday, June 30, 2023 at 23:59:59 UTC". The seconds encoding itself comes from RFC 9651 (below).
- [RFC 8594 — The Sunset HTTP Header Field](https://www.rfc-editor.org/rfc/rfc8594.html) — Informational, May 2019. `Sunset = HTTP-date` (`Sunset: Sat, 31 Dec 2018 23:59:59 GMT`), applying to the resource that returns it, and that clients "SHOULD treat Sunset timestamps as hints" — the syntax and status used in §10.
- [RFC 8288 — Web Linking](https://www.rfc-editor.org/rfc/rfc8288.html) — `Link` header syntax; §2.1.2, that an *extension* relation type "is a URI ... that uniquely identifies the relation type", SHOULD be under the control of whoever defines it, and SHOULD be all-lowercase. Registered relation types (§2.1.1) are bare tokens — the basis of the §8 Link relations row.
- [OpenAPI Specification (latest)](https://spec.openapis.org/oas/latest.html) — current release v3.2.0, 19 September 2025; the top-level object fields including `webhooks` and `components`; `info` requiring `title` and `version`.
- [OpenAPI Specification v3.1.0](https://spec.openapis.org/oas/v3.1.0.html) — confirms the top-level `webhooks` field for out-of-band, non-API-initiated requests, and the `securitySchemes`/`security` mechanism used in §14.
- [Migrating from OpenAPI 3.0 to 3.1.0](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0) — the Schema Object aligned to JSON Schema 2020-12 (3.0 was Draft 05), `nullable` removed outright, and the singular `example` replaced by the `examples` array.
- [draft-ietf-httpapi-ratelimit-headers — RateLimit header fields for HTTP](https://www.ietf.org/archive/id/draft-ietf-httpapi-ratelimit-headers-11.html) — `RateLimit-Policy` (`q` required, plus `qu`, `w`, `pk`) and `RateLimit` (`r` required, plus `t`, `pk`), the examples reproduced in §12, the `Retry-After` precedence rule, and the non-normative appendix listing the `X-RateLimit-*` conventions in current use and their interoperability problems. **An Internet-Draft, not an RFC.** Re-read 2026-09-28 (verified retroactively) for the parameter glosses that the 2026-09-28 trim added to §12. On that date the IETF datatracker listed -11 (dated 23 May 2026, expiring 24 November 2026) as the current revision. What the page confirms: `qu` "conveys the quota units associated to the "q" parameter" (§3.1; "The default quota unit is "requests"", and `content-bytes` and `concurrent-requests` are also defined in §3.1.2); `w` "conveys a time window" as an Integer "expressing an interval in seconds" (§3.1.3); `pk` "conveys the partition key", a Byte Sequence, on both fields (§3.1.4, §4.1.3). What it **contradicted**: the trim's first gloss of `t` as "seconds to reset". §4.1 marks `r` REQUIRED and `t` and `pk` OPTIONAL. §4.1.2 defines `t` as the effective window, "the number of seconds within which the client can use no more than the available quota", and adds "The client MUST NOT assume that all its service limit will be fully restored after the time indicated by the effective window parameter". A cross-skill review on 2026-09-28 corrected §12 to "effective window in seconds, not a guaranteed reset", which matches both passages (re-read the same day, verified retroactively; the datatracker still listed -11 as current). Also note that §12's "`Retry-After` never points earlier than the end of the effective window" tightens the draft's §6 "SHOULD NOT reference a point in time earlier than the end of the effective window" into a house rule; precedence is the draft's own "the Retry-After field MUST take precedence" (§7).
- [Google AIP-158 — Pagination](https://google.aip.dev/158) — the page-size/page-token/next-page-token contract, coercing oversize page sizes down, opaque tokens that must never confer authorization, an empty token as the only end-of-collection signal, optional and possibly estimated totals, and that adding pagination to an existing method is backwards-incompatible.
- [Google AIP-193 — Errors](https://google.aip.dev/193) — messages actionable for a technical reader and free of PII and internal implementation detail, plus machine-readable `UPPER_SNAKE_CASE` reason codes with domain and metadata (mapped here onto problem+json extension members rather than importing the gRPC envelope).
- [Google AIP-180 — Backwards compatibility](https://google.aip.dev/180) — the enumeration behind §10: removals and renames, type changes, newly required fields, changed defaults and default serialization, changed identifier formats, changed observable semantics, and the caution about adding response enum values.
- [Google AIP-136 — Custom methods](https://google.aip.dev/136) — colon-suffixed custom methods on the resource path, when they are justified over standard methods, and `GET` only for side-effect-free ones.
- [Zalando RESTful API Guidelines](https://opensource.zalando.com/restful-api-guidelines/) — the numbered MUST/SHOULD/MAY format and its positions on API-first, one self-contained spec, backward compatibility and tolerant readers, casing conventions, ETags, problem JSON, no stack traces, `Deprecation`/`Sunset` with monitoring, cursor-over-offset pagination, and `Idempotency-Key`. Rule titles verified verbatim: 113 "SHOULD avoid versioning", 114 "MUST use media type versioning", 115 "MUST not use URL versioning" — the source of the media-type option in §10. Rule 176 "MUST support problem JSON" cites RFC 9457 (verified in the page source; the rendered page truncates in some fetchers), consistent with §4.
- [Azure REST API Guidelines (microsoft/api-guidelines, vNext/azure)](https://raw.githubusercontent.com/microsoft/api-guidelines/vNext/azure/Guidelines.md) — URL and casing rules, `403` vs `404` for existence leaks, "never 404 for DELETE", omitting rather than nulling absent members and the last page's continuation link, the `202`-plus-status-monitor pattern with a 24-hour retention floor and the `Operation-Location` header carrying the monitor URL, the required dated `api-version` parameter, `Repeatability-Request-ID`, and its own non-problem+json error envelope. Presented here as a competing house style, not as consensus.
- [Stripe — Idempotent requests](https://docs.stripe.com/api/idempotent_requests) — the `Idempotency-Key` pattern: the first request's status and body stored and replayed including failures, UUIDv4 keys up to 255 characters with no sensitive data, parameters compared against the original, keys pruned after at least 24 hours, and results deliberately not saved for validation failures or concurrent collisions. Product decisions, cited as sane defaults. Re-read 2026-09-28 (verified retroactively): the page says Stripe saves "the resulting status code and body of the first request" and names no headers. §5's "and the headers its status requires (`Location` on a `201`)", added by a cross-skill review, is a house extension of §3's `Location` rule, not Stripe's.
- [Stripe — Webhooks](https://docs.stripe.com/webhooks) — the production webhook contract: HTTPS with TLS 1.2/1.3, timestamped HMAC-SHA256 signatures over the raw body with constant-time comparison and rejection of non-current schemes, a 5-minute default tolerance, secret rotation with overlap, "quickly return a successful status code (`2xx`) prior to any complex logic that could cause a timeout" with events processed on an asynchronous queue, at-least-once and unordered delivery with dedupe on event id, retries with exponential backoff, `3xx` treated as failure, and version-pinned immutable events. Also defaults, not standards.
- [OWASP API Security Top 10 — 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) — the categories behind §9 and §14 (the item numbers are trimmed from SKILL.md 2026-09-28): API1 broken object level authorization and API3 broken object property level authorization (§9), API4 unrestricted resource consumption (§9 limits), API9 improper inventory management (§14), API10 unsafe consumption of APIs (trimmed from SKILL.md 2026-09-28).
- [oasdiff — Preventing Breaking Changes](https://github.com/oasdiff/oasdiff/blob/main/docs/BREAKING-CHANGES.md) — the `breaking` and `changelog` subcommands, and the documented requirement that `--fail-on ERR` (or `WARN`/`INFO`) is what makes `breaking` "exit with return code 1"; without it the command reports and exits 0. This is the gate that mechanizes §10.
- [Spectral](https://github.com/stoplightio/spectral) — `spectral lint <file> [--ruleset ...]`, the built-in `spectral:oas` ruleset, and `extends` in `.spectral.yaml` (all from the README). The `--fail-severity` flag used in §15 is not in the README; it is defined in `packages/cli/src/commands/lint.ts` with choices `error|warn|info|hint` and default `error` — confirm it for the version you install.

Verified retroactively on 2026-09-28. These pages were read after the 2026-09-28 trim had already introduced the facts they support, so the rules were not derived from them (tier defined in [SOURCES.md](../../../SOURCES.md)). They are ordered specification first, then vendor and tool documentation:

- [RFC 9651 — Structured Field Values for HTTP](https://www.rfc-editor.org/rfc/rfc9651.html) — Standards Track, September 2024, obsoletes RFC 8941. §3.3.7 says Dates represent "a (possibly negative) delta in seconds from 1970-01-01T00:00:00Z, excluding leap seconds", serialized like Integers and "distinguished from them with a leading "@"". This is the basis of §10's "`@` plus Unix seconds" for `Deprecation`, which RFC 9745 §2.1 defines as such a Date (verified retroactively 2026-09-28).
- [RFC 3339 — Date and Time on the Internet: Timestamps](https://www.rfc-editor.org/rfc/rfc3339.html) — Standards Track, July 2002. §5.6 gives `date-time = full-date "T" full-time`, `full-time = partial-time time-offset`, and `time-offset = "Z" / time-numoffset`, so the offset is mandatory; §2 defines `Z` as "a UTC offset of 00:00". This is the basis of §8's Timestamps row and of the `?created_at_gte=2026-01-01T00:00:00Z` example that a cross-skill review put in §7 in place of a bare `2026-01-01`, which is a `full-date`, not a `date-time` (verified retroactively 2026-09-28).
- [OWASP API3:2023 — Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/) — under "How To Prevent": "avoid using functions that automatically bind a client's input into code variables, internal objects, or object properties ("Mass Assignment")", and "Allow changes only to the object's properties that should be updated by the client". That backs §9's "never to the persistence model". The page does not call for per-operation request schemas or warn against binding to a response schema; its only schema advice is "schema-based response validation". Those parts of §9's rule, added by a cross-skill review, are house decisions: a response schema carries server-owned fields that a caller must not set (verified retroactively 2026-09-28).
- [GitHub Docs — Workflow syntax for GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) — `jobs.<job_id>.steps[*].shell`. On Linux and macOS, an unspecified shell runs `bash -e {0}` and `shell: bash` runs `bash --noprofile --norc -eo pipefail {0}`. Under "Exit codes and error action preference": "By default, fail-fast behavior is enforced using set -e for both sh and bash." This is the source of "'set -e' (the GitHub Actions bash default)" in [`contract-gates.md`](contract-gates.md) (verified retroactively 2026-09-28).
- [GNU Bash Reference Manual — The Set Builtin](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) — under `-e`: "The shell does not exit if the command that fails is ... or if the command's return status is being inverted with !". This is why [`contract-gates.md`](contract-gates.md) ends every negated grep in `|| exit 1` (verified retroactively 2026-09-28).
- [GNU Bash Reference Manual — Exit Status](https://www.gnu.org/software/bash/manual/html_node/Exit-Status.html) — "Bash itself returns the exit status of the last command executed, unless a syntax error occurs". Together with the entry above, this is why a bare matching `! grep` fails the build only when it is the script's last line. As a local check (not a source), GNU bash 3.2.57 was run on 2026-09-28. `bash -e -c '! grep -q nullable: spec.yaml; echo still-running'` against a file containing `nullable:` printed and exited 0; `bash --noprofile --norc -eo pipefail` behaved the same. With `|| exit 1` added, it exited 1 (verified retroactively 2026-09-28).
- [FastAPI — Extending OpenAPI](https://fastapi.tiangolo.com/how-to/extending-openapi/) — "A FastAPI application (instance) has an .openapi() method that is expected to return the OpenAPI schema". `fastapi.openapi.utils.get_openapi` generates it from the path operations in `app.routes`, it is served at `/openapi.json`, and `openapi_version` defaults to "the latest: 3.1.0". This is what makes FastAPI the code-first case in §14, and the export §14 says to commit. The page says nothing about committing the export, reviewing its diff before the implementation, or failing CI on a stale export; those are house rules added by a cross-skill review (verified retroactively 2026-09-28).
