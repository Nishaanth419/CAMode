# Docker and Deployment Best Practices — Sources

Provenance for [`../SKILL.md`](../SKILL.md). This file is deliberately kept
out of the skill body so it costs no tokens at load time; read it to verify a
rule, not to follow one. Repository-wide provenance tiers and known gaps:
[SOURCES.md](../../../SOURCES.md).

Throughout this file, "this document" and section references such as section 2 point to
`../SKILL.md`, whose rules these sources support. This text was moved out of that
file verbatim, so "the rules above" likewise means the rules there.


Primary sources retrieved and read while writing this document. Undated entries were read on
2026-08-19, the date recorded for this skill in SOURCES.md; an entry or clause marked
"(checked 2026-09-28)" was read during the 2026-09-28 trim and supports a fact that trim introduced.

- [Docker Docs — Building best practices](https://docs.docker.com/build/building/best-practices/) — multi-stage builds, trusted and minimal base images, digest and package version pinning, one-concern-per-container, single `RUN` for `apt-get update`+`install` with list cleanup, sorted multi-line args, absolute `WORKDIR`, non-root `USER` and `gosu` over `sudo`, `COPY` vs `ADD`, `ENTRYPOINT`+`CMD` split, `set -o pipefail`, `.dockerignore`.
- [Docker Docs — Build secrets](https://docs.docker.com/build/building/secrets/) — `RUN --mount=type=secret` syntax, default `/run/secrets/<id>` target, `--secret id=,src=`/`env=` forms, `--ssh default`, predefined `GIT_AUTH_TOKEN`/`GIT_AUTH_HEADER`, and the warning that build args and env vars persist in the final image.
- [Docker Docs — Optimize cache usage](https://docs.docker.com/build/cache/optimize/) — instruction ordering, dependency manifests before source, `.dockerignore` for context size and cache stability, `RUN --mount=type=cache` and `--mount=type=bind`, registry cache for CI.
- [Docker Docs — Build context](https://docs.docker.com/build/concepts/context/) — that "the build client looks for a file named .dockerignore in the root directory of the context", and that the one documented alternative is a Dockerfile-specific ignore-file placed beside the Dockerfile and prefixed with its name (for example `build.Dockerfile.dockerignore`), which "takes precedence over the .dockerignore file at the root of the build context if both exist". This is the basis for the section 2 rule that a plain `.dockerignore` beside a Dockerfile outside the context root is ignored. The page documents no warning for an ignore-file in the wrong place, so "silently" is inferred from that absence, not quoted. (checked 2026-09-28)
- [Docker Docs — Build attestations (SBOM and provenance)](https://docs.docker.com/build/metadata/attestations/) — `--sbom=true`, `--provenance=mode=max`, in-toto format, attachment to the registry image index, and the loss of attestations with `--load`. Re-read on 2026-09-28, the page's "Driver and image store support" section now describes `--load` as a requirement, not a loss. For the `docker-container`, `kubernetes`, and `remote` drivers, "Pushing the result to a registry with --push keeps the attestations. If you load the result into the daemon with --load instead, the same image store requirement applies". That requirement is the containerd image store, because "The classic image store doesn't support image indices". The page's opt-out is "--provenance=false --sbom=false", and it states that "Provenance attestations with the mode=min level are added to images by default". This is the basis for the section 10 rule that a `pull_request` run gates a `--load` build with no attestations. (checked 2026-09-28)
- [Docker Buildx source — `build/opt.go`](https://raw.githubusercontent.com/docker/buildx/master/build/opt.go), with [`util/dockerutil/features.go`](https://raw.githubusercontent.com/docker/buildx/master/util/dockerutil/features.go) — the code behind the `--load` case above, read on the `master` branch. The `docker` exporter (`--load`) checks whether the daemon has the OCI importer, which `features.go` detects as the daemon's `driver-type` being `io.containerd.snapshotter.v1`, that is, the containerd image store. Without it, any attestation requested by flag fails the build with "docker exporter does not currently support exporting manifest lists". The default provenance is set separately, as `mode=min,inline-only=true`, only when no `--provenance` flag is given, and that check does not count it. So omitting `--sbom`/`--provenance` on the section 10 PR build avoids the error. This file does not show whether the default inline-only provenance survives `--load` into a classic store, and nothing was run locally because no Docker daemon was available. (checked 2026-09-28)
- [Docker Docs — Registry cache backend](https://docs.docker.com/build/cache/backends/registry/) — that this backend "works with the default `docker` driver only when the containerd image store is enabled. If the containerd image store isn't enabled, use a different driver" — the driver precondition noted in section 2.
- [Docker Docs — Build checks reference](https://docs.docker.com/reference/build-checks/) — the named rules listed in [`ci-gates.sh`](ci-gates.sh), and (on the [`CopyIgnoredFile`](https://docs.docker.com/reference/build-checks/copy-ignored-file/) rule page) that the check fires when a `COPY`/`ADD` targets a path excluded by `.dockerignore` (trimmed from SKILL.md 2026-09-28).
- [Docker Docs — Checking your build configuration](https://docs.docker.com/build/checks/) — that `docker build --check` exits non-zero when violations are reported, the `# check=error=true` directive, and the `BUILDKIT_DOCKERFILE_CHECK=error=true` **build argument** form.
- [Docker Docs — Start containers automatically (restart policies)](https://docs.docker.com/engine/containers/start-containers-automatically/) — that `on-failure` and the other restart policies react to a non-zero **exit code**, with no health-status-based restart documented; the basis for the warning in section 6 that Docker takes no action on an unhealthy container.
- [Compose file reference — Services](https://docs.docker.com/reference/compose-file/services/) — that `depends_on` supports `condition: service_healthy`, which requires the dependency to define a `healthcheck`; the one place a plain-Docker `HEALTHCHECK` changes behaviour rather than only reporting.
- [Docker Docs — Docker Scout quickstart](https://docs.docker.com/scout/quickstart/) — `docker scout quickview` / `cves`, and the policy areas (non-root default user, fixable critical/high, base image currency, attestations present) referenced in the CI gates.
- [Docker Docs — `docker scout cves` CLI reference](https://docs.docker.com/reference/cli/docker/scout/cves/) — `--exit-code` ("Return exit code '2' if vulnerabilities are detected") and `--only-severity`, which are what make the Scout step in section 10 an actual gate; no such flag is documented for `quickview`.
- [Docker Docs — `docker container run` CLI reference](https://docs.docker.com/reference/cli/docker/container/run/) — verified semantics for `--init`, `--read-only`, `--tmpfs`, `--cap-add`/`--cap-drop`, `--security-opt`, `--user`, `--memory`, `--cpus`, `--pids-limit`, `--restart`, `--stop-signal`, `--ulimit`, and the `--health-*` flags.
- [Docker Docs — Packet filtering and firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/) — that "When you publish a container's ports using Docker, traffic to and from that container gets diverted before it goes through the ufw firewall settings", and that with firewalld enabled Docker creates a `docker` zone with target `ACCEPT` plus a forwarding policy allowing forwarding from any zone into it. This is the basis for the section 8 statement that Docker-published ports bypass host firewall rules, which the 2026-09-28 trim made unconditional (it previously read "can bypass"). The page names ufw and firewalld; it does not claim every host firewall is bypassed. (checked 2026-09-28)
- [Docker Docs — Content trust in Docker](https://docs.docker.com/engine/security/trust/) — the page warning "Docker Content Trust (DCT) is being retired. The Notary v1 service at notary.docker.io will shut down on December 8, 2026"; the basis for excluding DCT from the section 9 signer choices. (checked 2026-09-28)
- [Docker Blog — Docker Content Trust: Retirement and Migration Guidance](https://www.docker.com/blog/docker-content-trust-retirement-and-migration-guidance/) (Julia Wilson and Aditya Tripathi, posted Jun 16, 2026) — the retirement schedule (4-hour write brownouts on Jul 14 and 15, 2026, 4-hour read brownouts on Aug 10 and 12, 2026, and "Dec 8, 2026 Full shutdown"); that only DCT trust operations are affected, while ordinary `docker pull` and `docker push` keep working; and that it names Sigstore/Cosign and the Notary Project's Notation as the replacement signers, the two options section 9 offers. This is a vendor blog post, not reference documentation; the docs page above states the same shutdown date. (checked 2026-09-28)
- [Dockerfile reference](https://docs.docker.com/reference/dockerfile/) — `USER` syntax and scope, and the distinction that `ARG` is not embedded in the image while `ENV` persists into running containers. Also (checked 2026-09-28) the instruction form `ARG <name>[=<default value>] [<name>[=<default value>] ...]`, which allows the single `ARG GIT_SHA VERSION BUILD_DATE` line in the section 2 example, and the warning that build arguments "are visible in the docker history command and in max mode provenance attestations". Also (checked 2026-09-28), under `COPY --chown`: "When using names instead of numeric IDs, BuildKit resolves them using `/etc/passwd` and `/etc/group` in the container's root filesystem. If these files are missing or don't contain the specified names, the build fails. Numeric IDs don't require this lookup." This is the basis for the section 2 statement that a named `--chown=app:app` fails the build if the user does not exist yet. That statement replaced an earlier "fails silently", which this page contradicts. The BuildKit reference below carries the same three sentences.
- [BuildKit Dockerfile reference](https://raw.githubusercontent.com/moby/buildkit/master/frontend/dockerfile/docs/reference.md) — shell-form `ENTRYPOINT` runs under `/bin/sh -c`, does not pass signals, and ignores `CMD`/run arguments; exec form runs as PID 1; build arguments are visible in `docker history`; `COPY --chown`/`--link`; `ADD --checksum`; and the `HEALTHCHECK` option defaults, including `--start-period=DURATION` (default: `0s`), cited in section 6.
- [OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) — the runtime hardening matrix: never mount the daemon socket or expose it over TCP, `--cap-drop all`, no `--privileged`, `no-new-privileges`, seccomp/AppArmor/SELinux, user-defined networks and interface-bound published ports, resource and ulimit caps, `--read-only` with `tmpfs` and `:ro` volumes, CI linting/scanning, rootless mode, and supply-chain controls.
- [NIST SP 800-190, Application Container Security Guide](https://csrc.nist.gov/pubs/sp/800/190/final) (Souppaya, Morello, Scarfone) — countermeasure themes used here: image vulnerability scanning and CVE gating, shrinking attack surface, image signing and verification, keeping cleartext secrets out of images in favour of external secret management, trusted registries, and runtime hardening.
- [The Twelve-Factor App](https://12factor.net/) — config in the environment, strict build/release/run separation, stateless processes, port binding, admin processes.
- [The Twelve-Factor App — IX. Disposability](https://12factor.net/disposability) — the SIGTERM contract for web processes and queue workers, job reentrancy and idempotency, fast startup, crash-only design.
- [The Twelve-Factor App — XI. Logs](https://12factor.net/logs) — unbuffered event stream to stdout; the app never routes or stores its own logs.
- [Kubernetes — Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) — probe roles and their differing consequences, the termination sequence (endpoint removal, `preStop`, SIGTERM, grace period default 30s, SIGKILL), `CrashLoopBackOff`.
- [Kubernetes — Configure Liveness, Readiness and Startup Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) — the `exec`/`httpGet`/`tcpSocket`/`grpc` handler examples and the startup-probe-covering-slow-start pattern.
- [Kubernetes — Liveness, Readiness, and Startup Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/) — the "Configuration fields" section, which is the source of the `timeoutSeconds` 1 default quoted in section 6 (the other defaults, `initialDelaySeconds` 0, `periodSeconds` 10, `successThreshold` 1, `failureThreshold` 3: trimmed from SKILL.md 2026-09-28), and the rule that liveness and readiness probes do not run until a configured startup probe succeeds. Also (checked 2026-09-28): when a readiness probe fails, "the EndpointSlice controller removes the Pod's IP address from the EndpointSlices of all Services that match the Pod"; "When your app has a strict dependency on back-end services ... The liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available"; and the caution that "Incorrect implementation of liveness probes can lead to cascading failures". These support the section 6 rule that dependency checks go in readiness, never liveness. The page does not discuss a dependency shared by every replica. The rule against a readiness check on a shared external API is the skill's own inference from the endpoint-removal behaviour: when the API is down, every replica fails readiness at once and the Service is left with no endpoints. The page does not state this.
- [Kubernetes — Container Lifecycle Hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/) — the three hook handler types, including "Sleep - Pauses the container for a specified duration", which is why the native `Sleep` handler is preferred over an `exec` sleep in section 5.
- [Kubernetes — Feature Gates](https://kubernetes.io/docs/reference/command-line-tools-reference/feature-gates/) — the `PodLifecycleSleepAction` gate ("Enables the sleep action in Container lifecycle hooks (preStop and postStart)"): alpha and off by default in 1.29, beta and on by default in 1.30 to 1.33, stable from 1.34. This is the basis for the section 5 instruction to check that the cluster version supports the native `Sleep` handler; the Container Lifecycle Hooks page above names the handler but gives no version. (checked 2026-09-28)
- [Kubernetes — Resource Management for Pods and Containers](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) — requests drive scheduling while limits are enforced at runtime; CPU throttling vs memory OOM kill; a limit with no request implies an equal request.
- [Kubernetes — Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) — rollouts trigger only on `.spec.template` changes, `maxSurge`/`maxUnavailable`/`minReadySeconds`/`progressDeadlineSeconds`/`revisionHistoryLimit`, and `kubectl rollout status`/`history`/`undo`. Also (checked 2026-09-28) the note that "when you roll back to an earlier revision, only the Deployment's Pod template part is rolled back". This is the basis for the section 11 statement that an app rollback leaves the schema in place.
- [Martin Fowler's bliki — Parallel Change](https://martinfowler.com/bliki/ParallelChange.html) (Danilo Sato, 13 May 2014) — that "Parallel change, also known as expand and contract, is a pattern to implement backward-incompatible changes to an interface in a safe manner, by breaking the change into three distinct phases: expand, migrate, and contract", and that "Most database refactorings follow the parallel change pattern, where the migrate phase is the transition period between the original and the new schema, until all database access code has been updated to work with the new schema." This is the source of the expand/contract name in section 11. It is a practitioner article, not a standard. The requirement that each release's migrations leave the schema usable by the previous release is the skill's own rule. (checked 2026-09-28)
- [Kubernetes — Configuration Best Practices](https://kubernetes.io/docs/concepts/configuration/overview/) — prefer controllers over naked Pods, keep manifests in version control.
- [Kubernetes — Images](https://kubernetes.io/docs/concepts/containers/images/#image-pull-policy) — the four `imagePullPolicy` defaulting rules quoted in section 9, and that the defaulted value is fixed at object creation and is not revised when the tag or digest later changes.
- [OCI Image Spec — Annotations](https://github.com/opencontainers/image-spec/blob/main/annotations.md) — the `org.opencontainers.image.*` keys used in the section 2 Dockerfile example.
- [Gitleaks README](https://github.com/gitleaks/gitleaks) — that "v8.19.0 introduced a change that deprecated `detect` and `protect`. Those commands are still available but are hidden in the `--help` menu", and that the current scanning commands are `git`, `dir`, and `stdin`; the basis for `gitleaks dir .` in section 10.
- [Trivy — Secret scanning](https://trivy.dev/latest/docs/scanner/secret/) — that "Secret scanning is enabled by default" for `trivy image` and can be isolated or disabled via `--scanners`; the basis for the dedicated secret gate in section 10.
- [GitHub Docs — Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) — `pull_request` as the event name used in section 10. Its "Workflows in forked repositories" note says: "With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository. The GITHUB_TOKEN has read-only permissions in pull requests from forked repositories." The page does not say that a same-repository pull request run must not push. The rule that PR code never writes to the release registry or its cache is the skill's own. (checked 2026-09-28)
- GNU Bash reference manual, `set` builtin (read locally via `man bash`) — that `set -e` does not exit "if the command's return value is being inverted via `!`", which is why section 10 forbids `!`-negated gates.
- [Docker Hub tag list for the `node` Official Image](https://hub.docker.com/v2/repositories/library/node/tags) — queried directly to confirm that `node` publishes `<major>.<minor>` and `<major>.<minor>.<patch>` variant tags (for example `22.23-slim`, `22.23.2-slim`), not only major-level ones; the basis for the section 1 instruction to check the registry rather than assume.
- [CIS Benchmark for Docker](https://www.cisecurity.org/benchmark/docker) — existence and scope of the consensus benchmark and its automated assessment tooling. No individual recommendation number is cited here because the benchmark PDF itself was not retrieved.
