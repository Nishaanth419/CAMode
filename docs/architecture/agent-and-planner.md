# Agent, routing, planner and answer trace

Moved out of the always-loaded CLAUDE.md. Read this when changing `agent.py`, `agent_graph.py`, `planner.py`, `tasks.py`, `router.py`, `model_gate.py`, `analysis_tools.py`, `charts.py`, the answer trace, or the local model setup. Eval commands are in [testing.md](testing.md).

## Modules

- **`app/agent.py`**: Provider selection (Ollama/OpenAI/Groq), request filtering, and the tool-calling loop (`stream_agent` yields `(event, data)` tuples; `run_agent` collects them into an answer, its trace, its recorded events and its task-contract verdict).
- **`app/agent_events.py`**: `RunRecorder` (turns stream events into the run's event log: `seq`, `atMs`, camelCase keys, tool arguments/results/errors redacted and capped, the answer reduced to its length), `summarize()` (call counts, failed tool calls, retries, token totals, termination) and `redact_trace_text()` (re-exported by `agent`).
- **`app/tool_results.py`**: Tool failure kinds (`invalid_arguments`, `rejected`, `unavailable`, `auth`, `failed`), `error_payload()` (`{error, errorKind, next_step}` for the model), `reported_error()` (a local tool's top-level `{"error"}`) and `argument_problems()` (missing required arguments and values outside an `enum`; types are deliberately not checked).
- **`app/agent_runs.py`**: Saved answer runs: `save_run()` (one sealed row per chat answer or failed attempt in `device` mode: question start, contract verdict, events, summary; never fails the answer), `list_runs()`, `get_run()`, `all_runs()` (export), `delete_run()`, `delete_chat_runs()`. Newest `KEEP_RUNS` (200), none older than the chat lifetime
- **`app/tasks.py`**: Task contracts: `contract_for(category, agent_type, offered_tools)` (`refusal`, `general_finance`, `goal_calculation`, `account_data`: required and allowed tools, whether a clarifying question counts, observed call budgets), `plan_contract()` (`multi_step`: one part per kind of task, each part's required tools checked on its own), `contract_for(..., budgets=)` (the general agent's own limits), `ANALYSIS_TOOLS` (never count as reading account data), `evaluate()` (a call refused before it ran, `invalid_arguments`, uses no tool), `facts_from_events()`, `is_account_tool()`.
- **`app/planner.py`**: Planned answers for messages with several kinds of task: budgets (`MAX_PLAN_STEPS` 4, `MAX_ADDED_STEPS` 2, `MAX_REPLANS` 2, `MAX_TOOL_CALLS` 8, `MAX_MODEL_CALLS` 6, `STEP_TIMEOUT_SECONDS`, `DEADLINE_SECONDS`), the `submit_plan` / `add_plan_steps` tools and prompts, `check_plan()` / `check_steps()` (offered tool, `tool_results.argument_problems()`, `after` naming only earlier steps, no repeated call, fix a rejected call once, never retry an unavailable one, at least one account step), `repaired_call()` (an Ollama "error parsing tool call" 500 whose quoted text needs only stray trailing characters removed or brackets closed), `PlanState` (`ready()`, `missing()`), `parts_covered()`. Pure; `agent` runs it.

- **`app/charts.py`**: Candlestick charts in answers filled from the OHLC tool result, and chart data kept out of the model's history.

- **`app/model_gate.py`**: Admission control and time budgets for model calls: `call(provider, request)` wraps every model HTTP call (`agent.py`'s three call sites and `router.classify`); Ollama calls take one of `concurrency()` slots (`MODEL_CONCURRENCY`, else `OLLAMA_NUM_PARALLEL`, else 1; an `asyncio.Semaphore` per event loop), a new chat waits at most `queue_seconds()` (`MODEL_QUEUE_SECONDS`, 20) and gets `ModelBusy` (`retry_after_seconds`), a chat already admitted waits within its budget. `chat_budget()` (`main.chat`: `CHAT_DEADLINE_SECONDS`, 240) and `call_deadline()` (the general agent's `DEADLINE_SECONDS`) bound calls, raising `DeadlineReached`; `remaining()`, `status()`, `reset()` (tests). In `agent.py` they become `error` events with codes `model_busy` (`retry_after`) and `chat_deadline`; `AgentRunError.code` / `.retry_after` carry them to `main.chat`. `wait_listener(callback)` (context manager: `callback` hears each model call that has to wait for a slot; the streaming chat uses it for `waiting` progress)
- **`app/chat_stream.py`**: Progress for a streamed chat: `sse()`, `ProgressMapper` (agent events to `{seq, kind, name, source, status}` only: fixed identifiers, tool names only when the contract allows them, `source` `indmoney` / `broker[:id]` / `analysis` / `saved`, never arguments, results or text), `response_event()` (the finished `Response` to the `answer` or `error` event, headers become `runId`, `questionsRemaining`, `creditsRemaining`, `creditsCharged`) and `events()` (`progress`, `: keepalive` every `KEEPALIVE_SECONDS` 15, then one `answer`/`error`; closing it never cancels the answer task)

- **`app/agent_graph.py`**: The general Portfolio Analyzer agent for `account_data` requests (see "General agent"): a LangGraph `StateGraph` over `AgentState` (`think → act → check → finish`), `Deps`, `ANALYSIS_GUIDE` / `guide(now)`, `run()`, `enabled()` (`AGENT_GRAPH_ENABLED`)
- **`app/analysis_tools.py`**: The agent's general tools: `ResultStore` (every result in full; `view()` gives a large one as an outline with a `resultId`), `inspect()` (`inspect_result`: path, text or object conditions, fields, sort, limit), `calculate()` (safe `Decimal` expressions), `option_strategy()`, `price_levels()`, `date_facts()`, `make_chart()` (bar/donut/line from a stored list, numbers read in code, registered in `ResultStore.charts` as `c1`...; `group_rest` sums the rest into "Other" in `Decimal`; rows without a value are skipped, never zero), `resolve_path()` (a path that is the unique tail of a real one, e.g. `top_holdings` → `figures.top_holdings`, is used; otherwise the error lists `pathsWithLists`), `tools()` (`ToolSpec`s), `ANALYSIS_TOOL_NAMES`; `calculate` also takes `id`/`value` items and names in any case
- **`app/options_math.py`**: Exact payoff analysis of any option position (`parse_legs()`, `analyze()`: net premium, max profit/loss or unlimited, breakevens, scenarios, rupees per lot, theta estimate)
- **`app/price_action.py`**: `parse_candles()`, `levels()` (latest completed session against the prior N sessions' high and low; today's candle left out before 15:30 IST)

## Local model and request routing

**Local model** (`agent.py`, `ollama/Modelfile`):
- `PROVIDERS["ollama"]` has no `key_env`: it is configured when `OLLAMA_MODEL` is set, is listed first and is the default `AI_PROVIDER`; the request goes to Ollama's OpenAI-compatible `/v1` API with a dummy key
- `provider_config()` returns `timeout` / `router_timeout` (`OLLAMA_TIMEOUT_SECONDS`, default 300, and `router.local_router_timeout()` (`OLLAMA_ROUTER_TIMEOUT_SECONDS`, 30) for Ollama; 120 s and `router.ROUTER_TIMEOUT_SECONDS` for cloud)
- Chat admission and budget (`main.chat`, `model_gate`): one answer in flight per profile (`main._chats_in_flight`, else `429 {chatInFlight}` with `Retry-After`), so monthly credits cannot be overspent by parallel answers; the answer runs inside `model_gate.chat_budget()` and `_run_agent_within_budget()` (an `asyncio.wait_for` backstop at the budget plus `CHAT_BACKSTOP_GRACE_SECONDS`); `model_busy` becomes `503 {modelBusy, retryAfterSeconds}` + `Retry-After`, `chat_deadline` `504 {chatDeadline}`; the daily question is released and nothing is charged. `app.js` shows all three as a plain assistant message
- Ollama's `/v1` API ignores per-request context options and silently truncates long prompts (4,096-token default on smaller Macs). `ollama/Modelfile` builds `ca-mode` (gpt-oss:20b, `num_ctx 32768`); after the first successful response of each answer, `_ollama_context_problem()` reads `/api/ps` and errors below `OLLAMA_MIN_CONTEXT` (16,384)
- Model choice and scores are in the README ("Use the local model"); re-run both evals with `--provider ollama` before changing it

**Request routing** (`router.py`, `agent.py`):
- `_route_request()` labels every message `off_topic`, `code_request`, `general_finance` or `account_data` with one classifier call (`router.classify()`: forced `classify_request` tool call, enum validated in code, user text sent as a JSON object of untrusted data, last 3 user turns as context). `off_topic` and `code_request` are refused without calling the answer model
- The classifier uses `OPENAI_ROUTER_MODEL` / `GROQ_ROUTER_MODEL`, else the provider's chat model. Any failure (HTTP error, 429, timeout, no or unknown category) falls back to the keyword rules (`_keyword_category()` over `_blocked_request_reason()` and `_requires_indmoney_data()`); `REQUEST_ROUTER=keywords` skips the classifier entirely (tests set this in `conftest.py`)
- The route is the first trace step (`kind: "route"`, `source: "model" | "keywords"`)
- Portfolio Analyzer gets `get_cas_holdings` (`snapshots.cas_tool()`) only when the profile has uploaded a CAS, and `get_mf_returns` (`snapshots.mf_returns_tool()`, read-only, `scheme` filter, `benchmark` enum (an unknown id is an error payload), payload under 5,500 chars via `mf_returns_payload()`, an account tool) when it has a ledger, with `agent.MF_RETURNS_RULES` in the prompt; the prompt says to state the statement date and never add CAS figures to INDmoney's; with a ledger it also gets `get_mf_tax` (`snapshots.mf_tax_tool(compute)`, read-only, `fy` (`^\d{4}-\d{2}$`, a bad year is an error payload with `fys`) and `include_planning`, payload under 5,500 chars via `mf_tax_payload()` (drops per-fund rows and the tax notes, caps excluded and unclassified funds at 10, then planning options and those lists at 5, then 2, then 0, counted in `omitted`), the profile's `taxSlabPct`, an account tool) with `agent.MF_TAX_RULES`; the keyword fallback knows LTCG/STCG, capital gains, exemption and harvesting words
- Portfolio Analyzer always gets its local snapshot tools; live INDmoney tools (and the must-call-a-tool retry) only for `account_data`
- Changing `ROUTER_PROMPT` means bumping `ROUTER_PROMPT_VERSION` and re-running `python -m scripts.eval_router --provider <p>` on `evals/request_routing.jsonl` (69 cases; keyword baseline 46/69, 66.7%; `ca-mode` 66/69 with `router.v2`, which names the user's own capital gains, exemption and harvesting as account data)
- The Ollama classifier call sets `temperature: 0`; at the model's default of 1 it occasionally labelled a price-chart request `general_finance`, so Portfolio Analyzer got no live tools. Cloud providers get no temperature because some reasoning models reject one
- `_contains_code_output()` replaces code-shaped model output (except `chart` blocks) with the refusal notice
- If Portfolio Analyzer was not given the live tools and the model writes a tool call as JSON text (`_looks_like_tool_call()`), the request is rerun once with `force_account_data=True` instead of showing the JSON

## Portfolio tools

**Portfolio tools** (`agent.py`, `snapshots.py`):
- `PortfolioContext` carries the local `LocalTool`s (`get_portfolio_snapshot`, `get_networth_history`), the profile text, cached MCP tools, and an `on_mcp_tools` cache callback
- With cached MCP tools (< 24h), the MCP session opens lazily on the first MCP tool call; snapshot-only answers make no MCP calls
- A failing local tool returns an error tool result pointing to the live tools only when they are offered. An MCP result flagged `isError` (e.g. an argument outside the tool's enum) raises `mcp_client.McpToolError` and goes back to the model as an error tool result with a `next_step`, so it can correct the call; it still counts as a tool call. Other INDmoney failures (transport, HTTP 5xx, JSON-RPC errors, a session that cannot be opened) also go back as an error tool result telling the model not to call again (a failed session is tried once per answer). Only `mcp_client.McpAuthError` (HTTP 401, or error text that reads as an auth failure) ends the request; `run_agent` raises `AgentRunError(auth_failed=True)` and `main.is_indmoney_auth_error()` checks that flag, never the message text, before refreshing the token
- Tool arguments that are not a JSON object are refused with an error tool result (the tool is not run on `{}`); the trace keeps the model's raw text. Provider timeouts and errors with empty messages (`httpx.ReadTimeout`) become a readable error and are logged (`provider_timeout`, `agent_run_failed`); `run_agent` never returns an empty answer
- Profile fields go into a labelled `<user_profile>` block in the portfolio system prompt as context, not instructions

- `stream_agent()` / `run_agent()`: OpenAI/Groq loop; retries once if the portfolio model skips tools; marks answers cut off by `finish_reason == "length"`

- `_fit_groq_context()`: trims history and tool results to `GROQ_INPUT_TOKEN_BUDGET`, always keeping the current question

## Answer trace and Activity

**Answer trace and Activity** (`agent.py`, `frontend/js/trace.js`, `pages.js`):
- `agent.redact_trace_text()` masks tokens, secrets, PINs, PAN and bearer/JWT strings in trace `arguments`, `result_preview` and `error` before the trace is sent or saved; `trace.js` `redactText()` repeats it for older saved chats
- `trace.js` (loaded after `finance.js`, exported for Node tests) renders the answer trace (`renderChatTrace()`: collapsed to one row, "How this answer was made · N steps" plus up to 3 labels from `traceHighlights()`), reads what an answer used off its trace (`answerSources()`: route, snapshot date from a `get_portfolio_snapshot` result preview, tools once each with calls and failures, the number check, saved context, model, omitted steps; a fact the trace lacks is left out; `snapshotLabel()`), the evidence card (`renderInvestigationCard(record, {chart})`) and Activity rows; it formats figures but never computes them. A step still `running` in a finished trace or run shows as *Did not finish*
- `#/activity` also lists saved answer runs (`GET /api/runs?limit=50`, loaded beside investigations; a failure there never hides them) with `trace.js` `renderRunList()`; `#/activity/answer-<id>` shows one with `renderRunCard()` (the question, the contract's checks, counts and tokens, and every recorded step via `runSteps()`). An answer's trace links there when the chat message has a `runId` (`X-Agent-Run` for a new answer)
- `#/activity` lists `GET /api/investigations?limit=50` with client-side filters (All/Running/Completed/Failed as `.filter-chip`s; no approval state exists); `#/activity/<id>` shows one run. Each list row (`activityItem()` / `runItem()`) is a card: status marker, title, outcome and meta, with Open / Open chat / Run again on the right (below them under 620px); status pills are neutral for Running, green for Completed, red for Failed; the run and investigation cards read at page size on Activity (`#activity-body` rules), compact under an answer. Lists are reconciled with `reconcileInvestigations()` (newer `updatedAt` wins, a finished run is never replaced by an older running copy) and out-of-order responses dropped with `createSequencer()`; polling (`pollDelay()`) runs only while a run is active and the page is visible
- `agent.bounded_trace()` caps a trace at `MAX_TRACE_STEPS` (12): the first 3 steps, an `{"kind": "omitted", "count": n}` step, and the last 8, so the final answer or failure always shows; `trace.js` renders it as "n steps not shown" and counts it in the total
- Recorded events (`agent_events`): `route`, `context`, `contract`, `model_call`/`model_result` (status, finish reason, tool names, prompt/completion tokens), `tool_call`/`tool_result` (`errorKind`), `retry` (`no_account_tool`, `goal_calculator`, `invalid_tool_call`, `rerun_with_live_tools`), `validation` (`code_output`, `numbers`, `length`, `task_contract`), `plan` (`stage`, `outcome`, `steps` or `reason`) and `plan_stop` (`reason`, `missing`) in planned runs, whose `tool_call`/`tool_result` also carry the plan `step`, `answer`, `error` (with a `code` such as `provider_timeout`, `unknown_tool`, `tool_call_limit`) and `termination` (`answered`, `refused`, `failed`, `auth_failed`). The trace adds `retry` and `check` steps and model `tokens`; a refusal gets no contract step
- Task contracts observe and never change an answer, with one rule enforced: an account-data question is satisfied only by an account tool (`tasks.is_account_tool`: snapshot, history, CAS, mutual fund returns and tax, investigation, fund comparison or any INDmoney tool), so the goal calculator alone triggers the `no_account_tool` retry. INDmoney calls with a missing required argument or a value outside the schema's `enum` are refused before the call (`invalid_arguments`); a local tool returning `{"error"}` is recorded as `rejected`
- `scripts/eval_tasks.py` grades task handling from the recorded events on `evals/agent_tasks.jsonl` (21 cases; `--dataset evals/multi_step.jsonl` for planned answers, also graded on plan events, `plan_stop`, tool order, repeated calls and budgets). Scripted mode (default, offline, also run by `tests/test_eval_tasks.py`) replays each case's model replies and checks the contract, verdict, termination and code, retries, tool error kinds and number check; `--provider ollama --runs 3` runs the 8 `live` cases on the real model with the real calculator, the synthetic snapshot and stubbed INDmoney behaviours, graded on contract, traced figures, expected figures, clarifying questions, invented amounts, rejected calls and model calls. Re-run it before changing the agent loop, the goal tools or the contracts; a new case needs `expect` (and optionally `live.grade`)
- Progress streams, the answer does not: `progressLabel(event, brokerNames)` in `trace.js` words each progress event while it is made, and the full trace arrives with the finished answer. "Run again" (failed/cancelled only) re-POSTs the same `baselineDate` on a click, never automatically

- Answer run routes: `GET /api/runs?limit=` (summaries), `GET`/`DELETE /api/runs/{id}` (unlocked). `POST /api/chat` saves the run and returns its id in `X-Agent-Run` (and `runId` in a 502 body, whose `error` is `main.chat_failure_message()` by the agent's error `code`: never the exception or provider text, which go only to the log and the saved run); the chat's assistant message carries `runId`. Runs go with their chat, history clearing, private mode, INDmoney disconnect and profile deletion, and are in the export as `agentRuns`

## Planned answers

**Planned answers** (`planner.py`, `agent._planned_answer()`):
- Only for Portfolio Analyzer, an `account_data` route, a goal tool offered and `context.task_parts(message)` naming both kinds (e.g. "why did my portfolio drop and is my house goal still on track"); `main.chat` passes it as `run_agent(..., plan_parts=)`. Everything else, including the `force_account_data` rerun, stays on the ordinary loop
- One forced `submit_plan` call (only that tool offered; the offered tools listed as data in the system prompt via `planner.tool_catalogue()`); a plan failing `check_plan()` or a failed planner call is a `plan` event with `outcome: "rejected"` and the reason, then the ordinary loop answers under the ordinary contract (a second `contract` event)
- The local model's habits are accepted, not rejected: `name`/`tool_name` for `tool`, `args`/`parameters` for `arguments`, `after` by position ("step1"); an unrecognised `after` ("0", a tool name) waits for every earlier step (arguments are fixed at planning, so `after` only orders). A reference to the step itself or a later one is still refused
- Steps whose `after` steps have finished run together (`asyncio.gather`, each under `STEP_TIMEOUT_SECONDS`; a timeout is `unavailable`); `_ToolRunner` serves both paths and opens the INDmoney session once under a lock. An auth failure ends the answer as before (`plan_stop` `error`, then `indmoney_auth`)
- Then one call offering only `add_plan_steps` (auto): a plain answer ends the run; added steps (at most 2, renamed `r1-…`) go through `check_steps()`; after `MAX_REPLANS`, a rejected addition or another tool, a last call with no tools answers with `planner.final_prompt()` naming what is missing. Past `DEADLINE_SECONDS` or `MAX_TOOL_CALLS` no new step starts
- `plan_stop` reasons: `complete` (every part has a succeeded tool), `clarify` (a part is not covered and the answer asks a question), `partial`, `budget`, `deadline`, `error`. The answer goes through `_guarded_answer()` (code output, charts, number check with `goal_maths`, length) like any other
- Re-run `python -m scripts.eval_tasks --dataset evals/multi_step.jsonl` (15 scripted cases; also in the test suite) and `--provider ollama --runs 3` (4 live cases) before changing the planner, its prompts or budgets

## General agent

**General agent** (`agent_graph.py`, `analysis_tools.py`; README "Multi-step analysis"):
- Portfolio Analyzer + `account_data` (and the `force_account_data` rerun) is answered by `agent_graph` when `AGENT_GRAPH_ENABLED` (default true); the previous loop and the `submit_plan` planner stay as the fallback when it is false. `conftest.py` and `scripts/eval_tasks.py` set it false because their cases script the previous loop; `test_agent_graph.py` and `scripts/eval_workflows.py` turn it on
- Nothing is written for a particular question: the model chooses every call. CA Mode adds the general tools (`inspect_result`, `calculate`, `option_strategy`, `price_levels`, `date_facts`, `make_chart`; `tasks.ANALYSIS_TOOLS` never count as reading account data), `ANALYSIS_GUIDE` (how to work, and facts about INDmoney's data: unlabelled expiries, `buy_price`/`sell_price`, `14d` is calendar days, `investment_code` as `fund_ids`...) with today's IST date and time, and bounded checks
- `act` runs a reply's calls together (`CONCURRENCY` 4, `STEP_TIMEOUT_SECONDS`), retries a timeout/429/5xx once (`transient_tool_error`), refuses an unknown tool, non-object or schema-failing arguments (`invalid_arguments`), a repeated call (`rejected`, pointing at its `resultId`) and calls past `MAX_TOOL_CALLS` (36) or `MAX_CALLS_PER_REPLY` with an error result the model can act on; a result made only of error fields (`tool_results.returned_error`) is `rejected`. INDmoney and saved-data results go into the `ResultStore`; analysis tool results do not
- `think` retries a malformed tool call (Ollama "error parsing tool call", Groq `tool_use_failed`; `_provider_call` marks it) twice, then asks for an answer without tools (`plan_stop` `partial`); at `MAX_MODEL_CALLS` (14), `MAX_TOOL_CALLS` or `DEADLINE_SECONDS` (180; a model call still running then is cut off) it asks once without tools (`plan_stop` `budget` / `deadline`). `check` sends back once an empty reply (`empty_reply`), an answer with no account tool (`no_account_tool`), a bar/donut/line chart block with numbers the model typed (`hand_written_chart`), no chart when the question asks to draw one (`no_chart`; `charts.asks_for_chart()`, not for price-chart or candle wording) and figures the number check cannot trace to the messages plus every stored result in full (`unverified_figures`); `finish` runs `_guarded_answer`
- LangGraph gives a branch function only the keys of its annotated state type, so every key a branch reads (`route`) is in `AgentState`
- Layouts recorded live on 2026-10-26 (read-only, values only for public market data) are in `tests/fixtures/indmoney_market.py` and `indmoney_tools.json`; the `user_watchlist` stock row layout is not recorded (the watchlists were empty)
- Before changing the agent, its tools or the guide, run `python -m scripts.eval_workflows` (scripted, also in the suite) and `--provider ollama --runs 3` (13 live cases, one a chart request and four on the mutual fund sample ledger `tests/fixtures/mf_tax_sample.py` (case `"mf": "sample"`; `get_mf_returns` / `get_mf_tax` outputs can be checked under `figures`), graded on the answer); `--baseline` runs them on the previous loop

## Charts from tool data

**Charts from tool data** (`charts.py`):
- `ground_candlestick_charts()` (run on every answer in `stream_agent`) replaces each candlestick block with the latest `get_indian_stocks_ohlc` result as compact `ohlc` rows `[label, open, high, low, close]`, titled with the tool's instrument name. Candles the model wrote (or elided) are always replaced; with no OHLC candles the block becomes `CANDLES_UNAVAILABLE_NOTE`. The prompt still asks the model for full candles: telling it to write a title-only block instead raised unsupported claims in the investigation eval (9/60 vs 4/60 answers), so that change was dropped
- `ohlc_candles()` searches the parsed result (including a JSON string under `result`) for rows with open/high/low/close and a date, dropping impossible rows
- In the general agent bar, donut and line charts come only from `make_chart`: the answer holds `{"ref": "c1"}` and `ground_tool_charts()` (in `_guarded_answer`, before the number check) puts the chart there, appends charts made but not placed, drops typed data charts (`HAND_WRITTEN_NOTE`) and unknown refs, and records a `charts` validation event; the previous loop keeps model-written charts
- `strip_chart_blocks()` replaces chart blocks in assistant history before it reaches the model; `app.js` `chartCandles()` reads both `candles` and `ohlc`, and an undrawable chart block shows a note instead of a blank space
